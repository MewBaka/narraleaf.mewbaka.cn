---
title: What a server protects
description: The Team 1.0 access model, its trust boundary, and the limits a deployment should plan around.
---

A Team server holds accounts, project documents, versions and the collaboration record. The repository's [security documentation](https://github.com/NarraLeaf/NarraLeaf-Team/blob/main/docs/security.md) carries the full model and accepted risks. This page is the deployment view.

## Access is per project

Each project has members with one role: owner, editor, reviewer or viewer. A project the caller has no role in is, to them, not there: every method and topic about it answers "not found" rather than "you may not".

Owners and editors may open the project repository. Reviewers and viewers may not; they read the project through Team. The version-control server cannot distinguish reading from writing, so a role that may not write is a role that may not open the repository.

Editors can be limited to story, characters, assets, UI, localization or game config. Team determines the area from the file an edit reaches, and anything unrecognised counts as game config. Restoring a version changes every area and needs all six.

An operator is an owner of every project. A new project starts with its creator as owner and every other account as editor. A new account starts as an editor of every existing project, so upgrading from 0.1.0 behaves as the old server did until an owner narrows a project. Review sensitive projects after an upgrade.

Only an owner or operator may take a project off the list. The repository remains in the store; the registry row, threads and comments attached to it are removed. Record the repository id before removal if the project may need to be registered again.

## What the connection rests on

Everything a client says arrives on one port behind one certificate. Team issues that certificate itself unless the organization supplied one. A person compares the fingerprint once over a channel other than the connection being trusted. Studio keeps the authority it was shown and refuses a different one later.

The web console runs on the same origin and certificate. Its session is an `HttpOnly`, same-origin cookie, revocable from the account's device list. Pages that render text written by other people are served under a policy that admits no inline script and no third-party origin.

Studio may sign in through OAuth with PKCE to a loopback redirect, or through the device flow. The password route is kept for older Studio builds. A server can require two-step sign-in, require SSO, issue API tokens and use password-reset links.

## What a token proves

A sign-in token is checked on every Team call: signature against a published key, issuer, audience, expiry, whether the account still exists and is not disabled or locked, and whether the token predates the account's last revocation.

A repository token is presented on the data connection instead. The version-control server checks its signature and expiry there and asks Team nothing further until it expires. Its lifetime is fifteen minutes by default, the longest an already-open data connection can outlive a revoked role.

## Who can do what

| Holder | Reaches |
| --- | --- |
| A project viewer or reviewer | The project through Team: files, versions, comments and review, as the role allows. No repository. |
| A project editor | The areas granted to them, and the repository only when they have all areas. |
| A project owner | Everything in that project, including members, settings, versions and removal from the list. |
| An operator | Every project, account, setting, signing key, storage area, backup and audit record. |
| Whoever holds the storage root | Everything, including the keys that issue tokens for any account. |

The last row is not a gap. A server is recovered from its own directory, so that directory is protected by machine permissions, disk encryption and backups.

## What is recorded

Every repository access decision is recorded. The console and `nlteam audit` read the record back. Collaboration records carry their author and time, and project work is credited to the person who did it.

## Reporting a vulnerability

Report privately through [GitHub's security advisory form](https://github.com/NarraLeaf/NarraLeaf-Team/security/advisories/new). Do not open a public issue for a vulnerability.
